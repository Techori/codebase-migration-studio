- Site themes live in `site-theme.ts`: the switch offers only dark, light and festive; festive keeps one festival colour palette while its decorations alternate on a shared wall-clock interval (same for every visitor), and each design is an isolated, removable class block in `src/styles.css`, and `__root.tsx` applies the saved theme before first paint with an inline boot script mirroring these rules (keep both in sync), so festivals can be added or retired without touching dark/light and hidden pictures never load.
- Education Support rules and payment-page links are browser-safe and tested; new acknowledgement numbers use a database trigger with permanent state/district codes and a bounded global sequence, preserving earlier references. Bank/KYC text is AES-GCM encrypted server-side, excluded from drafts/PDF/export, and decrypted only after admin authorization; approval is guarded by a database trigger requiring confirmed payment.
- Education staff access is separate from profiles; admin-assigned verified BDE/BDM accounts receive only own/team referral summaries without contact or KYC data and cannot confirm payments or approve applications.
- CRM memberships and employee profiles stay separate; RLS helper functions enforce own/team access, atomic invoker RPCs create/import leads, admin-only verified-account onboarding assigns access, and exact-reference support lookup projects only safe fields. The private CRM has its own unframed workspace and palette, separate from public site decoration.
- Website form → CRM lead routing lives in one AFTER INSERT database trigger per submission table (security definer, contact fields only, never bank/KYC, failures never block the submission), resolving the entered code to an active employee; unmatched leads stay ownerless for admin assignment via an RPC, so every form path routes identically.
- The app is hosted on Lovable and secrets stay in that deployment. Builds of this code served elsewhere (riloyd.in on another host and backend) send scholarship form and checklist actions from the browser to the published Lovable site's `/api/public/education/$action` (riloyd.in origins allowlisted, same validation, rate limits and sheet fallback), so every response reaches this project's database and Google Sheet; update the home address in `education-support/remote.ts` if the Lovable URL changes. Rate limits read the visitor IP from the hosting edge header.
- The scholarship form is staged (basic details issue the ack number, then payment, then the rest) and reopens with ack + date of birth + state; students pass the payment step and final submission only after a payment ID is shared (checked in the browser and on the server, admins exempt), so no unpaid form is completed. A Google Sheet keyed by ack number mirrors every start/submit/payment ID (masked bank/Aadhaar only, matched by header, grid grows itself); when the database fails at any step the sheet takes the change instead (new rows get a `B`-prefixed backup ack; rows already in the database are marked "Update pending" and copied back on the next reopen/final submit or admin sync), and visitors only see plain messages, never database errors, so no response is lost. A managed schedule calls `/api/public/jobs/education-sheet-sync` every few minutes to run the same sync automatically.
- The student AI checklist accepts only non-sensitive answers (category, class/course, fee type, state, age group, ticked items, a short note rejected if it contains long numbers, emails or IFSC codes), is rate-limited per visitor IP, and stores nothing, so no contact, bank or Aadhaar details reach the model.
